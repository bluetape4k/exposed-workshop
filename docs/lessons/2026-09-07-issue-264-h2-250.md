# 이슈 #264 H2 cross-session workaround 제거 lesson

## 배경

H2 `2.4.240`에서 provider metadata의 `CHECK (... IN (...))` 제약을 서로 다른
JDBC session에서 평가할 때 `BATCH_JOB_EXEC_STATUS_ACTIVE_KEY_CHK` 오류가
발생했다. 당시에는 전역 H2 버전을 바꾸지 않고 checkpointable batch 모듈의
test runtime만 `h2-v2-check-workaround = 2.3.232`로 고정했다. H2 upstream
수정이 포함된 `2.5.250`이 Maven Central에 게시되면서 이 우회 설정을 제거할
조건이 충족되었다.

## 결정

- 전역 version catalog의 `h2-v2`를 `2.5.250`으로 갱신한다.
- `h2-v2-check-workaround` version/library alias를 삭제한다.
- checkpointable batch 모듈은 module-specific 버전 pin 대신 전역
  `libs.h2.v2` alias를 test runtime에 사용한다.
- 회귀 테스트는 schema를 한 `Database` handle에서 생성하고 provider repository를
  별도 `Database` handle에서 실행해 cross-session 경계를 직접 고정한다.
- H2 upstream 수정이 확인되지 않은 상태에서 workaround를 먼저 제거하지 않는다.
  Maven Central의 POM/JAR 직접 응답과 실제 Gradle 해석을 함께 확인한다.

## 검증

- RED: H2 `2.4.240`을 임시로 해석했을 때 named regression이
  `BATCH_JOB_EXEC_STATUS_ACTIVE_KEY_CHK` 및 `23514-240`으로 실패했다. 내부 원인은
  H2 `The database has been closed [90098-240]`이었다.
- GREEN: H2 `2.5.250`으로 전환하고 workaround를 제거한 뒤 named regression이
  `1 passing`, `BUILD SUCCESSFUL`로 통과했다.
- H2 `2.5.250` POM과 JAR는 Maven Central에서 HTTP `200`으로 확인했다.
- `USE_FAST_DB=true ./gradlew :11-checkpointable-batch:test :05-ktor-exposed-integration:test
  --no-daemon --no-configuration-cache --no-build-cache --console=plain`은
  batch `9개`와 Ktor `UP-TO-DATE`로 `BUILD SUCCESSFUL`이었다.
- `./gradlew clean build --no-daemon --no-configuration-cache --no-build-cache
  --console=plain`은 `BUILD SUCCESSFUL in 11m 21s`로 종료했고, `1102 actionable
  tasks: 1100 executed, 2 up-to-date`를 기록했다. `exposed-shared-tests`는
  `156개` 테스트 중 `6 skipped`였다.

## 다음 적용 원칙

특정 모듈에만 적용한 dependency workaround는 upstream 수정의 release와
repository 게시를 직접 확인한 뒤 제거한다. alias를 새 버전으로 이름만 유지하지
말고, 전역 alias와 module scope를 다시 설계해 stale version·library alias가
남지 않았는지 `rg`, dependency resolution, named regression으로 함께 검증한다.
